## How it works

Authentication is [Better Auth](https://www.better-auth.com) 1.6.11 with three ways to sign in: **Google**, **LinkedIn** and **passkeys**, plus the Admin plugin. There are no passwords, no sign-up form and no emails.

- **Google** and **LinkedIn** are the only ways to create an account: the first sign-in creates the user. Signing in with either one later, with the same email, reaches the same user.
- **Passkeys** are added by a signed-in user ("Add a passkey" in the sidebar's account menu, or Settings → Security) and can then be used to sign in instead of Google or LinkedIn. Settings → Security (`/settings/security`) lists them, renames them, and deletes them after a confirmation. One passkey per account: both add buttons are disabled while the user has one (UI only; the server would accept a second). Adding one needs a sign-in from the last day (Better Auth's fresh-session rule). A passkey is bound to `BETTER_AUTH_URL`'s host name, so it only works on that host (`localhost` counts as secure in development; a plain-http LAN address does not).

| Piece | File |
| --- | --- |
| Better Auth config (server only) | `src/lib/auth.ts` |
| Browser client (`authClient`, `authClient.passkey`, `authClient.admin`) | `src/lib/auth-client.ts` |
| Auth endpoints (`/api/auth/*`) | `src/app/api/auth/[...all]/route.ts` |
| `getSession()`, `getSessionUser()`, `requireUser()`, `requireAdmin()` | `src/lib/session.ts` |
| The signed-in user's identity (`getIdentity()`, `requireIdentity()`, `requireIdentityId()`) | `src/lib/identity.ts` |
| Ownership lookups (`findOwnedAccount`, `findOwnedRun`, `findOwnedIdea`) | `src/lib/ownership.ts` |
| Guards for Server Actions (`requireOwnedAccount`, `requireOwnedRun`, `requireOwnedIdea`) | `src/lib/account-guard.ts` |
| Early redirect for visitors with no session cookie | `src/proxy.ts` |
| Sign-in page, and its Google, LinkedIn and passkey buttons | `src/app/(auth)/login`, `src/components/auth/` |
| "Add a passkey" (sidebar account menu, `useAddPasskey()`) | `src/components/add-passkey-button.tsx`, `src/components/user-menu.tsx` |
| Settings → Security → Passkeys (list, rename, delete) | `src/app/(app)/settings/security/` |
| Tables | `src/db/auth-schema.ts`, migrations `0014_auth_and_identity_owners.sql`, `0015_auth_passkeys.sql` and `0016_one_identity_per_user.sql` |

**Tables.** Better Auth's `user`, `session`, `account`, `verification` and `passkey` models are stored in `auth_users`, `auth_sessions`, `auth_accounts`, `auth_verifications` and `auth_passkeys`. `auth_accounts.password` is part of Better Auth's core schema and stays empty. The `auth_` prefix avoids a clash with `accounts`, which holds LinkedIn identities. Ids are uuids generated by Postgres.

**Ownership.** Each signed-in user owns **one** identity (`accounts` row), linked by `accounts.user_id` (`UNIQUE`). There is no identity switcher and no active-identity cookie: every page and action works on the user's identity, from `getIdentity()`. A user without one is sent to `/identity`, which creates it (with the AI setup assistant); the same page edits it later, and the other setup steps live under `/identity/…`. Creating a second identity is impossible: `createAccount` returns the existing one, and the unique constraint settles a race. Everything else (voice, goals, knowledge, preferences, schedules, runs, ideas, posts, media) belongs to the identity, so it belongs to its owner. An identity with `user_id = NULL` belongs to nobody and is never shown. Handles are not unique.

**Sessions** are checked against the database on every request; there is no cookie cache. Signing out or an admin revoking a session takes effect immediately.

**`proxy.ts` is not security.** It only checks that a session cookie is present, so visitors without one land on `/login?next=…`. It runs on pages only: API routes answer 401 themselves, and are kept out of the proxy so it never sits in front of their request bodies or cancel signals. A present cookie proves nothing. The real checks are in each page, Server Action and API route.

**Security decisions**

- **No passwords.** Email and password sign-in is off, so its endpoints (sign-up, sign-in, password reset) refuse every request.
- **Google and LinkedIn link by email.** A sign-in whose email the provider reports as verified joins the existing user with that email, confirmed or not (users left from the old password sign-up, or made by an admin). That is safe only because nothing else can create a way in: there are no passwords, and passkeys need a session. Neither is a "trusted provider", so an email the provider has not verified never links; the user sees "…this provider has not verified the address" and can sign in another way.
- **Passkeys need a session to add.** Only a signed-in user can register a passkey, and only to their own account. Signing in with an unknown passkey fails.
- **`?next=`** is only followed when it is a path inside the app (`src/lib/safe-redirect.ts`). Better Auth separately refuses callback URLs from other origins.
- **Roles cannot be self-assigned.** `role`, `banned`, `banReason` and `banExpires` are not user-settable (Admin plugin `input: false`); update-user ignores or refuses them.
- **Rate limiting** is Better Auth's built-in limiter, on in production. It keys on `x-forwarded-for`, so deploy behind a proxy that sets that header itself, otherwise clients can choose their own IP. It uses memory storage, so each server process counts separately.

## Setup

### Environment

Add these to `.env` (documented in `.env.example`):

| Variable | Required | Notes |
| --- | --- | --- |
| `BETTER_AUTH_SECRET` | Yes (production refuses to start without it) | At least 32 characters: `openssl rand -base64 32`. Changing it signs everyone out. |
| `BETTER_AUTH_URL` | Yes | The URL people open the app at, e.g. `https://linkedin.example.com`. Google and LinkedIn redirect back to it and passkeys are bound to its host name. Defaults to `NEXT_PUBLIC_APP_URL`. |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | At least one provider | Each button shows only when both of its values are set. Google and LinkedIn are the only ways to create an account; with neither, only existing passkeys can sign in. |
| `LINKEDIN_CLIENT_ID`, `LINKEDIN_CLIENT_SECRET` | At least one provider | See above. |
| `ADMIN_USER_IDS` | No | Comma-separated `auth_users.id` values that are always admins. See [Administrators](#administrators). |

Requests are also accepted from `NEXT_PUBLIC_APP_URL` when it differs from `BETTER_AUTH_URL` (e.g. a LAN address in development).

**Docker:** the Dockerfile builds with `npm ci`, so `package-lock.json` must include `better-auth` and `@better-auth/passkey` (run `npm install --package-lock-only`). It also copies `.env.example` to `.env` at build time. With an empty secret, `next build` logs "You are using the default secret" while collecting page data. The build still succeeds; provide `BETTER_AUTH_SECRET` at runtime.

### Database

Apply migrations `0014_auth_and_identity_owners`, `0015_auth_passkeys` and `0016_one_identity_per_user` with `npm run db:migrate`. `0015` only adds the `auth_passkeys` table. `0016` replaces `UNIQUE(user_id, handle)` with `UNIQUE(user_id)` and turns off the schedules of identities that were deactivated (deactivation no longer exists; `accounts.is_active` stays, unused). It fails while any user owns more than one identity; find them first with `SELECT user_id, count(*) FROM accounts WHERE user_id IS NOT NULL GROUP BY user_id HAVING count(*) > 1` and reassign or delete the extras. `0014`:

1. creates the four `auth_*` tables;
2. adds `accounts.user_id` (nullable, `ON DELETE CASCADE`: deleting a user deletes their identities and everything under them);
3. replaces the global `UNIQUE(handle)` with `UNIQUE(user_id, handle)`.

It is safe on existing data: existing handles were globally unique, and every existing identity gets `user_id = NULL`. It runs in one transaction, so there is no moment without a uniqueness rule. **After it runs, existing identities are hidden from everyone until they are assigned an owner** (next section).

### Google sign-in

1. In [Google Cloud Console](https://console.cloud.google.com/apis/credentials), create an **OAuth client ID** of type **Web application**.
2. Under **Authorized JavaScript origins**, add `BETTER_AUTH_URL` (e.g. `https://linkedin.example.com`, or `http://localhost:3000` for development).
3. Under **Authorized redirect URIs**, add exactly `{BETTER_AUTH_URL}/api/auth/callback/google`.
4. Configure the OAuth consent screen. The default scopes (`openid`, `email`, `profile`) are all that is used.
5. Put the client id and secret in `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`.

Sign-in always shows Google's account picker (`prompt: 'select_account'`).

### LinkedIn sign-in

1. In the [LinkedIn Developer Portal](https://www.linkedin.com/developers/apps), create an app. It must be linked to a LinkedIn Page (a company page you administer).
2. Under **Products**, add **Sign In with LinkedIn using OpenID Connect**. This grants the `openid`, `profile` and `email` scopes, which are all that is used.
3. Under **Auth → OAuth 2.0 settings**, add the redirect URL `{BETTER_AUTH_URL}/api/auth/callback/linkedin` (e.g. `http://localhost:3000/api/auth/callback/linkedin` for development).
4. Put the **Client ID** and **Primary Client Secret** in `LINKEDIN_CLIENT_ID` and `LINKEDIN_CLIENT_SECRET`.

LinkedIn sign-in only identifies the user. It is unrelated to the LinkedIn identities (`accounts`) the app writes posts for, and grants no access to post on LinkedIn.

## Rules for new code

Every Server Action and API route can be called directly with any arguments, so each one checks who is calling and what they may touch. `tests/auth-guards.test.ts` fails the build of any Server Action or API route that does not start with the session check.

**Server Actions**

```ts
export async function doSomething(rawAccountId: string, ...) {
  // 1. First, before any try/catch: redirects to /login without a session.
  const user = await requireUser()
  try {
    // 2. Check the row the client named belongs to this user.
    const account = await requireOwnedAccount(user.id, rawAccountId)
    // 3. Use ids from the checked row, and scope child rows by both ids:
    //    where(and(eq(goalsTable.id, goalId), eq(goalsTable.accountId, account.id)))
  } catch (error) { ... }
}
```

- Never take an owner id (`userId`) from the client; it is always `user.id` from `requireUser()`.
- For runs and ideas use `requireOwnedRun` / `requireOwnedIdea`, which check the owner through the identity.
- Data for the user's identity: `requireIdentityId()` resolves it on the server; prefer it to taking an identity id from the client at all.
- Missing and foreign rows must give the same answer (`NotFoundError`, "… not found"), so ids cannot be probed.
- `requireUser()` redirects by throwing. Inside a `try` it would be caught, which is why it comes first.

**Pages**: `requireUser()` at the top (the `(app)` layout does this too). Pages about the identity use `requireIdentity()` (redirects to `/identity` when there is none) or `getIdentity()` (null instead, for an empty state).

**API routes**: `getSessionUser()` first, then return a 401 JSON response yourself (`requireUser()` would redirect).

**Lookups** in `src/lib/ownership.ts` take the database as a parameter, so they can be tested against any connection.

## Legacy identities (owner backfill)

Identities created before sign-in existed have `user_id = NULL`: nobody can see them, and any data under them (runs, ideas, posts…) is hidden with them. Each must be assigned to its real owner. **Never assign them all to the first user who signs up.**

1. Ask each owner to sign in once with Google or LinkedIn, which creates their user.
2. List the unowned identities and agree, with the team, who owns each:

   ```sql
   SELECT id, name, handle, linkedin_url, created_at
   FROM accounts WHERE user_id IS NULL ORDER BY created_at;
   ```

3. Assign them in one transaction, checking before committing:

   ```sql
   BEGIN;

   CREATE TEMP TABLE identity_owners (
     account_id uuid PRIMARY KEY,
     owner_email text NOT NULL
   ) ON COMMIT DROP;

   INSERT INTO identity_owners (account_id, owner_email) VALUES
     ('00000000-0000-0000-0000-000000000000', 'owner@example.com');
     -- one row per identity

   -- Must return no rows: every owner has an account (emails are stored lowercase).
   SELECT o.* FROM identity_owners o
   LEFT JOIN auth_users u ON u.email = lower(o.owner_email)
   WHERE u.id IS NULL;

   -- Must return no rows: every listed identity exists and is still unowned.
   SELECT o.* FROM identity_owners o
   LEFT JOIN accounts a ON a.id = o.account_id AND a.user_id IS NULL
   WHERE a.id IS NULL;

   -- Must return no rows: each owner gets one identity and has none yet.
   SELECT lower(o.owner_email) FROM identity_owners o
   GROUP BY 1 HAVING count(*) > 1
   UNION
   SELECT u.email FROM identity_owners o
   JOIN auth_users u ON u.email = lower(o.owner_email)
   JOIN accounts other ON other.user_id = u.id;

   UPDATE accounts a
   SET user_id = u.id, updated_at = now()
   FROM identity_owners o
   JOIN auth_users u ON u.email = lower(o.owner_email)
   WHERE a.id = o.account_id AND a.user_id IS NULL;
   -- The UPDATE count must equal the number of mapping rows.

   COMMIT;  -- or ROLLBACK if any check failed
   ```

4. Ask each owner to confirm they see their identity.
5. Only once `SELECT count(*) FROM accounts WHERE user_id IS NULL` is 0 and owners have confirmed, add a migration that makes `accounts.user_id` `NOT NULL`. Until then, keep it nullable.

Background jobs are internal and still process runs for unowned identities. Nobody can start a run for one by hand any more, so only a schedule could. Scheduled runs currently never fire because of a separate bug in `src/jobs/scheduler.ts` (the slot is claimed twice, and the second claim always fails). If that is fixed before the backfill finishes, decide whether to skip schedules of identities with no owner, since nobody can review their output.

## Administrators

The Admin plugin is configured and its columns exist; there is **no admin UI yet**.

### Making someone an admin

Admins are never created automatically; the first user to sign up is an ordinary user. Use one of:

- **`ADMIN_USER_IDS`**: put the user's `auth_users.id` in the environment and restart. Best for the first admin. Remove it later if you prefer roles to live only in the database.
- **A reviewed database update**:

  ```sql
  UPDATE auth_users SET role = 'admin', updated_at = now()
  WHERE email = 'person@example.com';
  ```

  Have a second person review it, and record who ran it and why.

After that, admins can grant roles to others through the Admin plugin (`setRole`). Normal users cannot change their own role: the field is not user-settable, and every admin endpoint checks the caller's role on the server.

### Server-side checks

`requireAdmin()` (`src/lib/session.ts`) returns the signed-in user when they are an admin and 404s for everyone else, so admin pages do not reveal they exist. It applies the same rule as the plugin (`isAdminUser` in `src/lib/roles.ts`): role `admin`, or an id in `ADMIN_USER_IDS`.

### Building the admin panel later

1. Add `src/app/(admin)/admin/layout.tsx` that calls `await requireAdmin()`, with its pages under it. Call `requireAdmin()` again in any Server Action the panel adds.
2. Use the plugin through `authClient.admin` in the browser (`src/lib/auth-client.ts`), or `auth.api.*` with `headers: await headers()` on the server:

   | Task | Client method | Endpoint |
   | --- | --- | --- |
   | List and search users | `authClient.admin.listUsers({ query: { searchValue, limit, offset, sortBy } })` | `GET /api/auth/admin/list-users` |
   | Create a user (they then sign in with Google or LinkedIn using that email) | `authClient.admin.createUser({ name, email, role })` | `POST /api/auth/admin/create-user` |
   | Change a role | `authClient.admin.setRole({ userId, role })` | `POST /api/auth/admin/set-role` |
   | Ban / unban | `authClient.admin.banUser({ userId, banReason, banExpiresIn })`, `unbanUser({ userId })` | `POST /api/auth/admin/ban-user`, `/unban-user` |
   | List / revoke sessions | `listUserSessions({ userId })`, `revokeUserSession({ sessionToken })`, `revokeUserSessions({ userId })` | `POST /api/auth/admin/…` |
   | Impersonate | `impersonateUser({ userId })`, `stopImpersonating()` | `POST /api/auth/admin/impersonate-user`, `/stop-impersonating` |
   | Delete a user | `removeUser({ userId })` | `POST /api/auth/admin/remove-user` |

3. Banning revokes the user's sessions and blocks sign-in until `banExpires`.
4. Impersonation creates a session with `auth_sessions.impersonated_by` set to the admin's id. Impersonating other admins is refused by default. While impersonating, the app behaves exactly as that user, so ownership rules still apply. Show a visible banner when `session.impersonatedBy` is set.
5. Admin pages that show identities across users must query them explicitly (not through `getIdentity()`, which is the signed-in user's own), and only after `requireAdmin()`.
